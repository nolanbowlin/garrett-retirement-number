The short version

A light brand, a serif voice, one red

Peachtree Planning already has a clear identity and it is quieter than most financial brands. A white page, a classical serif at a light weight, generous space, and a single red used sparingly. The job of anything built here is to not break that.

Nothing in this document was invented or eyeballed from a screenshot. The palette, the type and the button geometry were read out of the live computed styles on peachtreeplanning.com on 19 August 2026. Where a value was genuinely absent from the site and had to be added, it is marked as such in the table below.

The one rule that matters most. The site is light. White page, ink text, red accents, occasional dark bands. An earlier draft of this whole package came back dark crimson on near black, taken from an older internal document rather than from the site, and it looked like a different firm. If a deliverable arrives dark, it is wrong.

Colour

Palette

One brand colour carries everything: Peachtree red. It appears 145 separate times on the home page and nowhere in large fields. Red is a signal, not a surface. It marks the thing you want clicked, the rule under a masthead, and the mark in the logo. When red starts filling panels, the brand stops reading as a wealth management firm.

Do not add accent colours

An early version of the scorecard ran a red, copper, green traffic light through the score. Copper and green are in no part of this palette, and a large orange number at the top of a results page read as another brand entirely. If something has to signal severity, it gets the brand red or it gets nothing.

Do not use #CC0000

It appears twice on the live site and is almost certainly a hardcoded hex inside one embedded widget. It is close enough to the real red to look like a mistake rather than a choice. #D2232A is the red.

Type

Two faces, both free

Tinos for headlines, Mulish for everything else. Both are Google Fonts, both are free to embed commercially, and one of them solves the hardest problem in HTML email by accident.

Tinos, headlines
Set at weight 400, even at 90px
The site never bolds a display headline
The live site runs its largest headline, "Empowering People to Create Generational Impact", at 90px in weight 400. That lightness at scale is most of the brand's character. Bolding a display headline makes it look urgent, and urgent is the opposite of what a wealth management firm is selling. Italic Tinos in red is the one permitted emphasis.
Tinos is metrically compatible with Times New Roman. In email, the fallback is dimensionally identical rather than merely similar, so a client with no webfont support renders the same layout.
Mulish, everything else
Body copy, UI, labels, buttons, fine print. A variable weight from 200 to 1000, though this system only ever uses 300, 400, 500, 600, 700 and 800. Falls back to Arial and Helvetica.
Weights in use
400 body copy  ·  600 question text  ·  700 buttons and labels  ·  800 rarely, for a UI heading

Form controls never go below 16px. iOS Safari zooms the page when a focused input is smaller than 16px and does not zoom back out on blur, so every screen after that point reads as overflowing to the right. This is not a type preference, it is a bug fix.

The trap

The primary lockup has a black wordmark. Put it on the slate band and the wordmark disappears, leaving a floating red mark. The instinct is to fix that in CSS with a filter or a colour override, which recolours the mark as well and leaves the lockup in two mismatched weights. Use the reversed file. That is what it is for.

Verified, not assumed

The reversed file was checked at the pixel level rather than taken on trust. Its wordmark region carries the same 4,941 opaque pixels as the light version, all of them white, with the red mark unchanged at 4 percent coverage. It is a genuine knockout, not the colour logo with a filter baked in.

Clear space and minimum size

  • Clear space on all sides is the height of the red mark. Nothing crosses it.
  • Minimum width 150px on screen. Below that the wordmark's thin strokes break up.
  • Render at 200px to 220px in an email masthead, 170px in a footer.
  • Never stretch, rotate, add a shadow, or place the lockup on a photograph.

Two versions of every document

Each email exists as a -template.html with merge tokens intact, and a -preview.html with every token filled so the layout and tone can be judged. The preview is generated from the template by build-previews.js, never hand maintained, because two copies of the same document edited in two places always drift, and the one that drifts is the one nobody opened recently.

Email safety

What breaks email, and how these files avoid it

The problemWhat these files do
Outlook renders with Word, which ignores flexbox, grid and most modern CSSTable layout throughout, every style inlined, role="presentation" on layout tables
Outlook will not draw a rounded button from CSSA VML roundrect fallback wrapped in an [if mso] block, with the same URL in both halves
Gmail clips a message over roughly 102KB and hides the footer, including the unsubscribe linkLargest template is 28KB. Check the size after adding images or long copy.
Gmail strips much of a <style> blockThe style block is progressive enhancement only. Nothing in it is load bearing.
Some clients mangle a raw @ in downloaded HTMLEncoded as &#64; in every address
Images hosted somewhere you do not control disappearServed from a repo we own via GitHub Pages. Mail already delivered cannot be repaired.
Replacing an image breaks mail already sent, because Pages caches hardNever overwrite a shipped file. Add a new filename and point new sends at it.
Dark mode inverts a light template unpredictablyExplicit color-scheme and supported-color-schemes set to light, and real background colours on every cell rather than inherited ones
